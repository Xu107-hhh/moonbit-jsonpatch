# 设计决策 FAQ

这个文档回答"为什么这样设计"——不是"做了什么"（README 已回答），而是每个关键选择背后的取舍。按三个主题组织：数据通路、操作语义、diff 与工程化。

## 一、指针与不可变更新（数据通路）

### Q1 为什么自己实现 JSON Pointer 解析，而不复用现成库？

MoonBit 生态里没有独立的 RFC 6901 指针包（mooncakes 全库检索确认过，这正是本项目填补的空缺）。而 pointer 只需要一个小而精确的子集语义：切分 `/`、处理 `~0`/`~1` 转义、识别规范数组索引。自己实现的成本低于引入一个不存在的依赖，且错误行为完全可控。

### Q2 `~0` / `~1` 转义为什么必须支持？

JSON 对象的 key 可以包含 `/` 和 `~` 本身（例如 `{"a/b": 1}`）。如果不转义，指针 `/a/b` 就无法区分"a/b 这个 key"和"a 下面的 b"。RFC 6901 规定 `~0` 表示 `~`、`~1` 表示 `/`，解析器必须还原，同时拒绝 `~2` 这类非法转义——宁可报错也不猜。

### Q3 数组索引为什么拒绝前导零（`"01"` 不是索引 1）？

RFC 6901 要求数组索引是"规范十进制"：`0` 合法，`01` 不合法。原因和 URL 里的规范形式一致：同一个位置必须只有一种写法，否则 `/arr/01` 和 `/arr/1` 是否指同一元素会产生歧义（对象 key 里 `"01"` 完全合法，两者必须能区分）。长度上限（9 位）防御超 int 范围的溢出。

### Q4 `-` 为什么只在 add 操作里合法？

RFC 6902 只定义了 add 到 `/arr/-` 表示追加到末尾。对 replace/remove 来说"末尾之后的位置"不存在，指向它就是错误。这个约束在解析层就拦下，而不是等到查数组时才失败。

### Q5 为什么库是不可变的——每次修改都返回新文档？

三个理由：**失败零副作用**——patch 应用到第 N 个操作失败时，原文档完好如初（有专门的测试 "inputs are never mutated" 证明），调用方可以直接重试或换策略；**可回滚**——保留旧引用就等于保留了历史；**并发安全**——读旧文档的代码不受写操作影响。这是把"补丁应用"做成事务的关键。

### Q6 不可变的代价是什么？为什么接受？

代价是每次操作复制从根到目标路径上的容器（对象是整个 Map，数组是切片拷贝），规模随文档大小线性增长——基准测试如实记录了这一点（10 万键对象上 100 个操作约 2.9 秒）。接受它是因为：绝大多数真实 patch 文档远小于这个规模；换来的是 Q5 的全部保证；且数据是透明的——README 的性能表让用户自己判断合不合适，大文档热路径可以选 merge patch（只递归变更分支，快三个数量级）。

### Q7 为什么不实现持久化数据结构（persistent Map）来降低复制成本？

那是一个独立的大型工程（HAMT 等），会显著扩大项目边界、引入自己的风险面。本项目定位是"小而正确、边界清晰的 RFC 实现"——先把语义做满（108/108），把成本模型量出来（benchmarks），把优化空间留在明处。

## 二、六种操作与错误模型（操作语义）

### Q8 move 为什么实现为"先 remove 再 add"？

RFC 6902 对 move 的定义就是"从 from 移除、加到 path"。拆成两步复用了已经过官方套件验证的 remove/add 代码路径，语义等价、代码更少、出错面更小。

### Q9 为什么禁止 move 到自己的子路径（如 `/a` move 到 `/a/b/c`）？

那会构成自嵌套：目标位置的"新值"正是包含目标位置的对象本身，结果要么丢数据要么产生无穷结构。实现上用一个 proper-prefix 检查（from 是否是 path 的严格前缀）在应用前拒绝，错误信息明确指出。

### Q10 test 失败为什么中止整个 patch，而不是跳过继续？

RFC 6902 规定 patch 是原子的：要么全部应用，要么整个无效。test 的语义是前置条件断言——它失败意味着"文档已经不是你以为的样子"，后续操作建立在错误假设上，继续执行是危险的。examples/ai 演示了这个特性如何用来拒绝过期的并发编辑。

### Q11 错误报告为什么带 index / op / path 三元组？

用户拿到的应该是"第几个操作、什么类型、卡在哪个路径、为什么"，而不是一句 "failed"。`PatchError` 携带操作序号、操作名、路径、错误类别和消息；数组越界类错误还会带上数组实际长度（PR #5 的改进），例如 "array index 5 is beyond the end of the array (length 2)"。

### Q12 为什么用 Result 表达失败，而不是 panic？

"路径不存在"对 patch 来说不是程序 bug，而是业务上的正常输入错误——调用方必须能处理它（回退、重 diff、报 400）。Result 把处理义务强制到类型系统层面，`fn main` / 演示代码里才显式 abort。

### Q13 add 和 replace 有什么区别？为什么 add 到已存在的对象成员是覆盖，到数组却是插入？

replace 要求目标必须已存在（否则报错，防止拼错路径悄悄创建）；add 在对象上"有则覆盖、无则创建"，在数组上是插入（后续元素后移），`-` 追加。这些都是 RFC 6902 的直接规定，测试逐条对照官方用例。

## 三、diff、merge 与工程化（质量保障）

### Q14 diff 为什么不追求"最小补丁"？

最小 diff 是编辑距离问题（O(n·m) 动态规划），对大文档代价高，而且"最小"不等于"语义正确"（把 `"a":1` 改成 `"a":2` 的最小解可能是 replace 整个对象）。本项目 diff 的承诺是：**正确**（apply 回去一定得到目标文档，全测试覆盖）、**稳定**（同样输入永远同样输出）、**可读**（操作对应人能理解的变更）。keyed diff（Q15）是针对"语义正确"的定向增强。

### Q15 keyed diff 为什么要求相对顺序一致、不建模 move？

带 move 的数组 diff 有本质歧义：`[A,B,C]` → `[C,A,B]` 可以是"A、B 各前移"也可以是"C 移到头部"，不同答案Patch 大小差数倍，且 move 必须拆成 remove+add（RFC 6902 无 move-from-diff 的惯例）。我们选择覆盖最常见的场景——增、删、改、原位递归——要求公共元素相对顺序不变；一旦发生重排序就整体回退到位置 diff，正确性永远优先于聪明。

### Q16 已经有 JSON Patch 了，为什么还要 RFC 7396 merge patch？

两个标准服务不同场景，生态里是并存的：JSON Patch 精确到路径、支持前置条件（test），适合工具间协议；merge patch 简单声明式（"对象递归合并、null 即删除"），适合配置更新和 LLM 输出整段修改。提供两个入口让用户按场景选，基准数据也支持这个选择（merge 快 2–3 个数量级）。

### Q17 官方测试套件（json-patch-tests）怎么接入的？为什么 vendor 进仓库？

用 Python 生成器（`tools/gen_suite.py`）把 117 个官方 JSON 用例编译成 MoonBit 黑盒测试（跳过上游标记 disabled 的 4 例，实际 108）。vendor 的理由：CI 离线可复现、版本锁定（升级 fixture 是显式 commit）、许可证兼容（Apache-2.0 项目 vendoring Apache-2.0 fixtures，归属在 `suite/fixtures/README.md` 完整注明）。

### Q18 测试为什么分黑盒（*_test.mbt）和白盒（*_wbtest.mbt）？

黑盒测试只能看到公开 API——官方套件全部走黑盒，保证测的是用户实际拿到的行为；白盒能看到私有函数，用于指针解析这类内部单元（比如空 token 的边界）。两层各司其职，官方套件 108/108 是对外承诺，内部单元测试兜底实现细节。

### Q19 playground 的产物怎么保证没坏？

GitHub Actions 把库编译成 JavaScript 部署到 Pages；验证不是"看一眼页面"，而是把**线上部署的 patch.mjs 下载回来在 Node 里直接调用**，覆盖 apply 成功/失败、diff、merge、解析错误五条分支。本地与 CI 产物哈希不同（平台差异）但功能验证一致。

### Q20 基准测试为什么固定随机种子？

`benches/` 用 32 字节固定种子的 chacha8 生成文档和补丁，每台机器测的是完全相同的输入，数字可复现、可对比（两次连跑中位数偏差 0.4%）。README 声明了环境（Windows/wasm release），明确绝对值随机器浮动、量级与比例才有参考意义。

附：与新项目集成常见追问——

- **"如果文档很大怎么办？"** 用 merge patch，或把热数据放在数组（连续拷贝比 Map 重建快一个数量级）；性能表给出具体量级。
- **"和 tiye/recollect 什么关系？"** recollect 用私有 PatchOp 结构、自动创建缺失路径（RFC 6902 明确禁止的行为）、5 月起休眠；本项目实现标准 RFC 文档格式，边界写在 README "Related work"。
- **"错误处理怎么迁移到我的服务？"** `apply` 返回 `Result[Json, PatchError]`，`PatchError.kind` 可匹配（PathNotFound/Conflict/TestFailed/...），index/op/path 直接拼进 400 响应。
